# 静态可行性与架构审查

审查日期：2026-10-12。只基于源码/项目说明静态检查；没有运行安装、迁移、服务或测试命令。本文件不代表运行验收。

## 产品判断

产品方向可行，但目前更适合定位为“人工把关的新媒体运营辅助工作台”，而非无人值守自动运营。选题是否有价值取决于具体平台、垂类和用户反馈；三个关键产品输入当前均未确定，因此不能合理承诺平台趋势采集、内容表现或变现能力。

先以一个垂类、一个账号、一个渠道验证闭环。首批可用 RSS 作为外部公开信息来源，验证来源留痕、选题去重和人工评分流程；它不能代表平台热榜或账号后台数据。只有确认平台并得到官方 API/授权能力之后，才应规划平台数据接入与发布。

## 当前代码快照

- FastAPI：`/health` 和 `/topics/score`；没有持久化 API、身份验证或审核页面。
- 评分：趋势、受众需求、竞争优势、变现潜力的加权评分。原实现没有拒绝 NaN/Infinity，现已增加有限数校验与大权重缩放，避免数值溢出。
- 数据：新增 SQLAlchemy 2 模型，覆盖 topics、content_items、content_metrics；来源 ID 唯一约束、内容状态、审核状态、成本和观测窗口都有字段。
- 迁移：新增 Alembic 初始迁移；默认 SQLite 便于单机开发，可经 `DATABASE_URL` 切换 PostgreSQL。应用启动不自动修改数据库。
- 采集：新增 RSS 2.0/Atom parser、限定 HTTPS/超时/响应大小的拉取函数及按来源 ID 幂等入库函数。不模拟登录，不抓取社交网页，不杜撰热度数值。
- 测试：新增 RSS/Atom 解析、HTTPS 拒绝、重复入库和非有限评分的单元测试；由于用户明确要求不操作本机命令，全部未执行。

## 主要缺口与风险

1. Feed 的授权、稳定性、条款和更新频率需逐个确认；当前没有配置默认 feed 或定时任务。
2. 采集函数尚未接入 FastAPI/n8n 调度、日志、重试和告警；数据库约束是并发重复写入的最终保障，但并发冲突的恢复策略尚未实现。
3. 选题评分是规则计算，不是经验证的预测模型；现有字段没有热度输入，不能把 RSS 采集误称作平台趋势监测。
4. 没有 LLM provider、模型调用预算、内容事实核查、人工审批界面或发布硬门禁；目前没有任何自动发布路径。
5. 内容模型有 AI 生成标记状态字段，但生成文件元数据和发布时的显式声明尚未实现。生成合成内容标识相关规定自 2025-09-01 起施行，后续内容生产/导出/发布流程必须结合适用规定和平台要求验证。
6. FastAPI 当前没有鉴权、CSRF/速率限制、生产部署配置；只适合本机开发，不应直接暴露公网。PostgreSQL/n8n Compose 是示例服务，没有包含本项目 API 容器。
7. README 原本同时声称 SQLite/PostgreSQL 方向不清，本轮已明确 SQLite 默认、PostgreSQL 可配置；模型迁移仍需在 SQLite 和目标 PostgreSQL 上实际验证。
8. 项目树不在 Git 仓库中（此前检查父目录和项目目录均无 Git 元数据），因此无法提供 diff/提交状态；建议先由项目维护者确认仓库根目录。

## 架构建议

```text
公开授权数据源 -> collectors -> provenance/dedup -> topics
                                          |
                                          v
评分策略 -> topic review -> content draft -> compliance/fact-check -> human approval
                                                                  |
                                                           disabled publisher
                                                                  |
发布后官方指标接口 -> content_metrics -> reports -> scoring feedback
```

采用 SQLAlchemy/Alembic 做持久化边界；采集器保持与平台发布器分目录；模型适配器只经统一接口调用并执行 token/请求预算；审批记录必须成为 publisher 的硬前置条件。SQLite 用于单机试做，确认并发和部署需求后再迁移到 PostgreSQL。n8n 应仅负责编排，业务状态、去重和审批规则留在应用/数据库中。

## API、账号与费用预估

- **现在的阶段：**不需要社交平台账号或平台 API；公开 RSS/Atom 只需选定 feed 并确认其许可。SQLite、SQLAlchemy、Alembic、FastAPI、pytest 均为可本地运行的软件，无外部 API 费用。PostgreSQL/n8n Compose 自托管的软件本身不计托管费，但需要机器资源和维护时间。
- **LLM 阶段（可选且后置）：**需选一家支持中国大陆可用、数据处理条款满足需求的模型 API，并创建 API Key/配置额度和限额。按 DeepSeek 官方页面当前高峰价示例，每百万输入 token ¥2、每百万输出 token ¥8（空闲时段约半价）。若每月生成 100 条，每条约 5,000 输入 token 与 2,000 输出 token，则约 ¥2.60/月高峰价；这是粗略纯文本示例，不含改稿、长上下文、图片/视频模型、汇率或价格变动。实际必须按 provider 返回 usage 记账。
- **平台阶段（待选定）：**需相应主体/账号、开发者平台应用、平台审核、用户授权及具体内容/数据权限。抖音、小红书、微信公众号的开放范围、申请门槛和账号费用彼此不同，不能在平台未选定时给出可信的 API 可用性或费用承诺；本项目暂不申请、不连接。
- **合规运营成本：**AI 生成合成内容标识、来源/版权核查、人工审核时间，以及后续存储/备份/监控均需纳入预算；相关要求依内容类型、服务角色和平台规则进一步核验。

价格参考（官方文档，查询日 2026-10-12）：[DeepSeek 模型与价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)、[百炼模型价格](https://help.aliyun.com/zh/model-studio/model-pricing)。内容标识规则：[国家网信办《人工智能生成合成内容标识办法》](https://www.cac.gov.cn/2025-03/14/c_1743654684782215.htm)。

## 下一步顺序

1. 确认平台、垂类、目标受众、内容形态及账号所有者/操作者。
2. 在授权数据源确认后，装依赖、运行现有测试、校验 Alembic 在 SQLite 与计划使用的 PostgreSQL 上的升级/降级，再修复发现的问题。
3. 添加采集服务层测试（HTTP mock、超时/尺寸限制、重复项/事务回滚），并记录每个 feed 的授权依据、抓取频率和删除策略。
4. 做选题审核队列和状态审计；随后做 LLM adapter 与 token 预算、事实核验及 AI 标识字段流转。
5. 最后再申请并实现单一平台的官方授权 adapter；发布默认关闭，先人工复制粘贴验证，不要自动发布。
